# Metadata on the wire, 2026-11-23

Scope: how much a stanze server can learn about a call, what can be removed from
its view, and in which order. Status: design note; phases 1 and 2 are
implemented.

## Threat model

The server (signaling plus embedded TURN) is honest but curious, or it is
compromised later: an operator can read every frame it relays, and a dump of its
memory covers every room alive at that moment. The TLS terminator in front is
part of the same party. A peer in the room is not an attacker; a network
observer is out of scope, because TLS and DTLS/SRTP already cover that.

Content is already out of reach: names, chat, file offers, file bytes and media
frames are sealed in the browser. This note is only about what remains.

## What the server sees today

| Signal | Detail | Consequence |
| --- | --- | --- |
| IP address | per WebSocket, and per TURN allocation | links a guest to a network |
| room id | 16 random bytes | a link, not an identity |
| passphrase | clear in the `join` frame | sees it, cannot keep it |
| SDP | codec list, direction, DTLS fingerprints | browser and device fingerprint |
| ICE | candidate addresses | local and public addresses of both ends |
| routing | `from` and `to` on every relayed frame | who is in a call with whom |
| toggles | `mic`, `cam`, `deaf`, `screen`, `hand` in clear | activity pattern per peer |
| sizes and timing | every frame, every relay allocation | who talks, how much, when |

Two consequences matter more than the rest. First, the passphrase is visible,
so the operator can join any room it wants to read the metadata of, and it can
sit in the middle of a first contact between two guests that have never met.
Second, SDP and ICE are visible, so the operator learns the address pairs that
were tried even when the media goes direct.

## Goals

1. The server never sees the passphrase and cannot MITM a first contact.
2. The server never sees SDP or ICE.
3. The server does not learn the toggle state of a peer from a cleartext frame.
4. Frame sizes stop being a fingerprint of what was sent.
5. The peer graph and the traffic volume stay visible; goal 5 is to document
   that limit, not to remove it.

## Phases

Each phase is independently shippable and leaves the product working.

### Phase 1: length hiding for sealed payloads (done, 2026-11-23)

Pad the plaintext before it is sealed, in fixed buckets of 512, 2048 and 8192
bytes and whole multiples of 8192 above that, with the padding field dropped on
receipt. The outer `enc` frame is already opaque, so this is a client-only
change and an old and a new client interleave. `padRoundTripOk` runs in the
post-quantum self test and proves the buckets and the round trip on every page.
Removes the size fingerprint of chat lines, names and offers, not of media
frames, which are sealed inside the frame transform.

### Phase 2: sealed negotiation (done, 2026-11-23)

The offer/answer/ICE exchange used to happen before any pair key existed, so the
server read it. The pair handshake already ran over the WebSocket in `enc`
frames, so the only work was to move the negotiation behind those keys: a
description leaves as `{k: 'sdp', d, s}` and a candidate as `{k: 'cand', c}`,
both sealed with the pair chat key. The server now has no description field at
all, answers a clear `offer`, `answer` or `ice` with `error: sealed-only`, and
relays the blob. A client that still sends one is told to reload and the peer
hears nothing.

Two consequences. A candidate can arrive before the answerer has a connection,
so it is held per pair until the offer is applied. And the peer is visible as a
tile before its connection exists, which the waiting room already needed.

### Phase 3: passphrase without disclosure

Replace the clear passphrase with a PAKE run between the two browsers, with the
server as a dumb relay. The passphrase then never reaches the server, a wrong
one costs one failed handshake, and a first contact cannot be steered. The room
passphrase stops being a server-side gate, so the waiting room and the admission
rules must be re-expressed on the client side, where the keys are.

### Phase 4: toggles sealed

Send `mic`, `cam`, `deaf`, `screen` and `hand` as one sealed copy per peer
instead of one cleartext broadcast. The server keeps only what the admission
rules need, which after phase 3 is nothing.

### Phase 5: traffic shaping

Pad sealed media frames to a bucket inside the transform, and optionally hold a
low constant rate between pairs. Buckets cost bandwidth on silence; a constant
rate costs more and is visible as such. Both blunt timing analysis, neither
removes it.

## What cannot be removed

- **The routing.** A mesh server must know which peer id sends to which, so the
  call graph is visible. An SFU would know more, a mixnet would cost latency.
- **Volume and timing.** Even with fixed frame sizes, the total per allocation
  and the moments it grows say who talks. Cover traffic moves the line, not the
  problem.
- **The addresses.** Direct media shows the peer address to the peer; relayed
  media shows both ends to the relay. Relay-only hides the local address from
  the other guest and hands it to the operator instead.
